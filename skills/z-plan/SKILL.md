# z-plan

**Thesis projects** (`Type: thesis` in STATE.md): follow the Plan row and the rules in `~/.claude/skills/z/THESIS.md` instead of the steps below.

0. **Prior art.** If STATE.md links no research or teardown file and the work parses external formats (transcripts, configs, APIs), ask the `researcher` for a teardown of 1–2 reference implementations (`reverse-engineer-anything` only for shipped binaries/bundles). Its "bugs not to repeat" become acceptance criteria in step 2.
1. **Review the plan.** Big or new product work: gstack `/autoplan` (CEO → design → eng review; it auto-decides). Smaller or purely technical work: `/plan-eng-review` only. A prototype or spike (one module, ~10 files or fewer, no data, auth, money or migrations): `/plan-eng-review` scoped to architecture, failure modes, test plan and "does any requirement contradict a constraint?", plus a one-line feasibility probe per toolchain or OS assumption. If a review reports its outside voice unavailable, run the `reviewer` on the plan file in fresh context as the outside voice (contradictions, infeasible steps, missing failure modes) and record its findings in the design doc. Add `/plan-design-review` when there is meaningful UI. With `Autonomy: full`, answer the reviews' questions yourself with the recommended option and log them in Decisions (FS-Systems: one question per design issue was what made the user grant full autonomy).
2. **Make tasks.** Ask the `planner` to turn the reviewed plan into acceptance criteria and an ordered task list; include the project's learnings (`~/.claude/skills/gstack/bin/gstack-learnings-search --limit 10`), the user's matching feedback memories and the matching section of `~/.claude/team-templates/stacks.md` in its brief. For UI work, ask for acceptance criteria at desktop and 390px phone widths, in Safari/WebKit as well as Chromium. Save its plan verbatim to `.claude/team/plan-<milestone>.md` and link it from STATE.md `Plan:`. Bring its open questions to the user (`guided`), or close them with its recommendation and log them (`full`).
3. **Pick a mode** (see "# Agent team" in `~/.claude/CLAUDE.md`): Pipeline for most work; Team only if the work splits into separate file areas — then assign file ownership per teammate.
4. Write tasks (with owners), mode and the test plan path into STATE.md. Set `Stage: build`, Next action `/z-build`. `guided`: get the user's OK on the plan before building. `full`: show the task list in a few lines and start. Either way, freeze it: `cp plan-<milestone>.md plan-<milestone>.approved.md`. Later changes to acceptance criteria need the user's OK, logged in Decisions.
